# Migração para v2.2 — papéis de interface

A v2.2 foi desenhada para permitir migração sem cortar conectividade durante o upgrade.

## 1. Atualize código e módulos

Mantenha inicialmente:

```bash
INTERFACE_POLICY_MODE="compat"
```

Nesse modo, `INPUT_TRUSTED_INTERFACES` continua produzindo os ACCEPTs genéricos da v2.1.

## 2. Classifique as interfaces reais

Use:

```bash
ip -br link
ip -br -4 addr
ip route
```

Então configure, por exemplo:

```bash
WAN_INTERFACES="eth1"
LAN_INTERFACES="eth0"
VPN_INTERFACES="wg0"
```

Não copie esses nomes sem verificar o servidor.

## 3. Revise os serviços locais

As regras TCP/300 do legado agora estão em `LOCAL_INPUT_RULES`. Remova entradas para interfaces não usadas e confirme as origens autorizadas.

Exemplo:

```bash
LOCAL_INPUT_RULES=(
    "name=admin-lan iface=@lan proto=tcp port=300 src=any"
    "name=admin-suporte iface=@wan proto=tcp port=300 src=203.0.113.10/32"
)
```

## 4. Diagnóstico em modo compat

```bash
./firewall_unidades.sh diagnose
./firewall_unidades.sh check --resolve
./firewall_unidades.sh generate 192.168.11.1
```

Revise `.firewall-v2/runtime/current/iptables.rules`, em especial a chain `INPUT`.

## 5. Ative `roles`

Depois de confirmar os papéis:

```bash
INTERFACE_POLICY_MODE="roles"
```

Nesse modo:

- WAN não recebe ACCEPT genérico;
- LAN/VPN recebem a confiança de interface;
- sobreposição de papéis falha na validação;
- WAN presente em `INPUT_TRUSTED_INTERFACES` falha na validação;
- `INPUT_TRUSTED_SOURCES` fica limitado a LAN/VPN.

Execute novamente:

```bash
./firewall_unidades.sh diagnose
./firewall_unidades.sh check --resolve
./firewall_unidades.sh generate 192.168.11.1
```

## 6. Aplique

Somente após revisar o ruleset gerado:

```bash
./firewall_unidades.sh apply 192.168.11.1
```

O backup/rollback da v2 continua disponível:

```bash
./firewall_unidades.sh backups
./firewall_unidades.sh rollback
```

## `rp_filter`

O comando `diagnose` mostra `rp_filter` global e por interface. O valor `1` é strict reverse-path filtering; em topologias multi-WAN ou com roteamento assimétrico, ele pode exigir revisão. A v2.2 não altera sysctl automaticamente.

## Observação para inbound

A v2.2 não cria DNAT/publicações externas. Ela prepara o fundamento de segurança para o próximo módulo: qualquer futura regra inbound terá de declarar uma WAN explícita e nunca dependerá de uma interface WAN genericamente confiável.
